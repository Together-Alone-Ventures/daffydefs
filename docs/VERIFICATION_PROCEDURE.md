# DaffyDefs CVDR Verification Procedure

This document defines the technical verification procedure for a DaffyDefs deletion receipt. It is not the end-user demo walkthrough; that will be published separately.

## Inputs

For a receipt generated by a DaffyDefs profile deletion, the verifier needs:

- the downloaded CVDR JSON;
- the public Internet Computer trust root / certificate-verification rules;
- for V4, the DaffyDefs source/build materials in this repository.

The downloaded JSON should be supplied to the verifier **as exported by DaffyDefs**, without field removal, re-encoding, or manual transformation.

## Verification model

### V1 — internal consistency

Recompute the receipt's hash/preimage relationships and require them to match the values carried by the receipt.

### V2 — certified commitment

Validate the embedded certificate against the IC trust root and require its certified data to match the receipt commitment, including delegation/canister-range checks.

### V3 — attested code identity

For `mktd02-v4`, validate the archived `module_hash_certificate` and require it to certify the exact path:

`/canister/<receipt.canister_id>/module_hash`

The certified module hash must equal the module hash bound into the receipt. Certificate ordering and the finalisation-delay rule are also checked.

This is archival evidence: a later canister upgrade does not invalidate it.

### V4 — code provenance

V4 asks whether the module hash attested for this receipt corresponds to the profile-canister WASM rebuilt from the disclosed source, dependency resolution, toolchain and build recipe.

The supplied reference verifier deliberately prints V4 as **NOT EVALUATED**. V4 is established by the rebuild-and-compare procedure below.

## Reference-verifier invocation modes

### Downloaded JSON file

This is the primary demo path because it tests the exact export the user receives:

```bash
tools/cvdr-verify/bin/linux-x86_64/mktd02-verify \
  --receipt-file <downloaded-receipt.json>
```

For source-built use, substitute the path to your own `mktd02-verify` executable.

### Network fetch

A receipt can also be fetched by canister and receipt ID:

```bash
tools/cvdr-verify/bin/linux-x86_64/mktd02-verify \
  --canister <profile-canister-id> \
  --receipt-id <64-hex-receipt-id>
```

The current DaffyDefs reference tool defaults to `https://ic0.app`. Use `--network <URL>` only when deliberately selecting another IC endpoint.

The DaffyDefs path:

- gates its process exit on V1, V2 and V3;
- reports live module corroboration as `INFO` only;
- reports tombstone persistence as `INFO` only;
- prints `V4 — code provenance: NOT EVALUATED`.

## Verification depth options

### Option A — supplied reference verifier

Run the downloaded receipt through the supplied executable. This is the convenience path for V1–V3.

The executable is not a trust anchor. A verifier may inspect/build the source or implement the checks independently.

### Option B — independently obtain the current module hash from ICP

A convenient command using `dfx` is:

```bash
dfx canister info <profile-canister-id> --network ic --identity anonymous
```

The output includes a line of the form:

```text
Module hash: 0x<64-hex-sha256>
```

This is a convenience client path, not a requirement to trust `dfx` as part of the receipt. The underlying public certified-state item is:

`/canister/<profile-canister-id>/module_hash`

and contains the SHA-256 of the **currently installed** canister Wasm. A verifier who prefers not to rely on `dfx` may implement the certified `read_state` request and certificate verification directly.

This is **current-state corroboration only**. If the profile canister has been upgraded after deletion, the current hash may legitimately differ from the archival hash preserved by the receipt.

### Option C — compare with the DaffyDefs release record

Compare the receipt's attested module hash with the expected profile module hash in `RELEASES.md`.

A match shows that the receipt's code identity matches the DaffyDefs release identity recorded by TAV. It does not independently prove that the disclosed source builds to that hash.

### Option D — full V4: rebuild and compare

Run:

```bash
bash scripts/build-profile-repro.sh
```

The final comparison artifact is:

```text
wasm_out/profile_canister.wasm
```

Compute:

```bash
sha256sum wasm_out/profile_canister.wasm
```

Current candidate:

```text
cb16ee538cd0dfc13ea3847a04b4b6c05f29ff9ad764d65cb52b9619a4af28c9
```

V4 is established for a receipt when the hash reproduced from the disclosed source/build procedure equals the module hash attested for that receipt.

Do not substitute the factory hash, frontend asset hash, bulletin-board hash, or verifier-binary hash.

## Container reproduction

For the pinned Debian environment:

```bash
bash scripts/build-capsule-container.sh
```

This packages tracked files only, embeds the capsule commit as packaging metadata, validates that identity in the container, and invokes the same canonical profile build script.

## Worked example 1 — fresh downloaded JSON; live code unchanged

This example uses the exact JSON export from a fresh mainnet DaffyDefs deletion.

```bash
tools/cvdr-verify/bin/linux-x86_64/mktd02-verify \
  --receipt-file <downloaded-receipt.json>
```

Receipt identity:

```text
Canister : 4gjva-liaaa-aaaaj-qseba-cai
Receipt  : 7ee5651b6ed53667d46ae54ae950a93a60b8c99dbd2277681625b15e34c0a4a6
```

Key output:

```text
V1: PASS — all 4 hashes independently recomputed and match
V2: PASS (receipt-contained mode) — embedded certificate valid, certified_data matches receipt commitment
V3 — attested code identity: SUBNET-ATTESTED — code identity certified by the subnet (finalization delay 1.7s)
V4 — code provenance: NOT EVALUATED (see published verification procedure)
INFO — live module corroboration (non-gating): MATCH — canister code unchanged since deletion
INFO — tombstone persistence (diagnostic, non-gating): PASS — tombstone intact, state hash matches
portable exit: 0
```

This illustrates the ordinary case: the downloaded JSON verifies, the archived V3 code identity is subnet-attested, and the current live module still matches the receipt-attested code.

## Worked example 2 — archival receipt after a later upgrade

This example fetches the July ceremony receipt by canister and receipt ID:

```bash
tools/cvdr-verify/bin/linux-x86_64/mktd02-verify \
  --canister y5izv-byaaa-aaaaj-qsdfq-cai \
  --receipt-id 0eceff7de5785e5d50bedca0cb3553409ba6ef6c5e2929715f903b48ff6abf70
```

Key output:

```text
V1: PASS — all 4 hashes independently recomputed and match
V2: PASS (receipt-contained mode) — embedded certificate valid, certified_data matches receipt commitment
V2 warning: certificate/receipt timestamp delta exceeds 300s (set CVDR_V2_CERT_TIME_WARN_SECS to adjust warning threshold)
V3 — attested code identity: SUBNET-ATTESTED — code identity certified by the subnet (finalization delay 0.9s)
V4 — code provenance: NOT EVALUATED (see published verification procedure)
INFO — live module corroboration (non-gating): MISMATCH-EXPECTED — canister upgraded since deletion (receipt remains valid under prior code version)
INFO — tombstone persistence (diagnostic, non-gating): PASS — tombstone intact, state hash matches
ceremony exit: 0
```

The `MISMATCH-EXPECTED` is not a receipt failure. It demonstrates why the receipt preserves an archival module-hash certificate: the canister can later be upgraded while the V3 attestation for the earlier deletion remains valid.

## Current evidence status

The candidate profile WASM has been reproduced in multiple clean same-host configurations and in a pinned Debian container built from a tracked-files-only capsule with no TAV credentials. These runs produced the same post-shrink profile hash.

No reproduction on physically distinct hardware is claimed. The published recipe enables any third party to perform an independent rebuild.

The final live-demo claim remains pending until the approved controller-window deployment ensures newly minted profiles use this candidate profile WASM and a fresh exported receipt attests the same module hash.
